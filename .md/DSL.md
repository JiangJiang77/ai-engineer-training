# 组件 01：DSL（规则语言）

> **组件定位一句话（先给你标准答案）**
> **DSL 的作用：把“不能交给 LLM 的确定性决策”，从代码和 prompt 里剥离出来。**

如果你能把这句话消化掉，DSL 已经学会一半了。

---

## 🟦 阶段 1：理解关（今天完成，60–90 分钟）

### 1️⃣ DSL 在 Agent 系统里的真实位置（非常重要）

你现在的技术栈里：

```
用户输入
   ↓
LLM（理解语义）
   ↓
DSL（判断是否允许 / 是否符合规则）   ← DSL 在这里
   ↓
LangGraph（决定流程走向）
   ↓
LLM / Tool（执行）
```

👉 **DSL 不是“理解用户”
👉 DSL 是“限制系统行为”**

这是第一道认知门槛。

---

### 2️⃣ DSL 解决的是什么工程问题？

请你对照这张表（能对上，才算理解）：

| 问题       | LLM | DSL |
| -------- | --- | --- |
| 模糊语义理解   | ✅   | ❌   |
| 规则一致性    | ❌   | ✅   |
| 权限 / 白名单 | ❌   | ✅   |
| 参数上下界    | ❌   | ✅   |
| 可审计性     | ❌   | ✅   |

👉 **凡是你不希望“模型临场发挥”的地方，都是 DSL 的领地。**

---

### 3️⃣ 最小 DSL 示例（你脑子里必须有）

不谈 grammar，先谈“形态感”：

```dsl
version: 1.0

rule heat_time:
  if user_intent == "modify"
     and new_time <= 60
  then allow
  else reject
```

你现在不需要：

* AST
* 类型系统
* 优雅语法

👉 **只需要：人能读、机器能判**

---

### 4️⃣ 阶段 1 打勾清单（现在就对）

* ⬜ 我知道 DSL 不是 prompt
* ⬜ 我知道 DSL 不是配置文件
* ⬜ 我知道 DSL 的产出是 **true / false / decision**
* ⬜ 我知道 DSL 不参与“生成”，只参与“约束”
* ⬜ 我知道 DSL 一定在 LLM 之后、执行之前

👉 这 5 条如果有一条模糊，先别急着写代码。

## 🟨 阶段 2：控制关（明天 / 后天，30–45 分钟）

### 目标

> **不用 Lark，不用 DSL 文件，你也知道 DSL 在干嘛**

### 低配实现（非常关键）

请你脑补或真的写出这样的代码：

```python
def check_rule(context):
    if context["intent"] != "modify":
        return False
    if context["new_time"] > 60:
        return False
    return True
```

👉 **这就是 DSL 的“本质”**

Lark / grammar / parser，只是把这件事：

* 变得可配置
* 变得可维护
* 变得能给非程序员用

---

### DSL 最容易被误用的 3 个地方（记住）

1. ❌ 把“推理逻辑”写进 DSL
2. ❌ 把 DSL 当成 prompt
3. ❌ 让 DSL 决定“怎么做”

👉 DSL 只回答一类问题：

> **“允不允许 / 合不合法 / 走不走这一步？”**

---

### 阶段 2 打勾清单

* ⬜ 我能用 if / else 模拟 DSL 规则
* ⬜ 我知道 DSL 不该访问外部系统
* ⬜ 我知道 DSL 的输入是「已结构化的数据」
* ⬜ 我知道 DSL 不做循环、不做规划
* ⬜ 我知道 DSL 是“被调用者”，不是“流程控制者”

## 🔥 DSL 专属「掌握判定题」（非常关键）

> **如果让你现在设计一个 Agent，你会把下面哪些逻辑放进 DSL？**

* 是否允许修改配置
* 是否超过最大执行次数
* 用户是不是管理员
* 如何生成回复文案
* 如何选择 Tool

✅ 正确答案是：**前 3 个**

如果你直觉就能选对，说明你已经站在**工程视角**了。
